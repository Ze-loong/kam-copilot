# F15 企业微信集成 — 设计文档

> **本功能为设计稿，尚未实现（Roadmap）。** 当前提供本地顾问侧边栏演示；以下 `WxWorkAPI` 接口与异常分层是未来企微接入方案。

## 一、为什么是"mock级别"，边界画在哪

F15 真实接入需要企微开发者凭证和企业认证；当前仅保留接口设计，待具备接入条件后再验证网络请求、权限和消息同步。

但"mock级别"不等于"随便写写"。这份设计文档要讲清楚的是：即使不连真实企微服务器，`WxWorkAPI`这个类依然要按"未来能无缝替换成真实实现"的标准去设计——方法签名、返回结构、异常处理这三层，都要跟一个真正对接企微API的实现保持一致，唯一的区别只是"方法体内部是真的发HTTP请求，还是构造一份假数据返回"。这样以后如果真的申请了企微测试账号，只需要替换方法体内部的实现，不需要改调用方（`sub_tag_node.py`等）的任何代码。

## 二、接口设计：三个公开方法 + 一个内部方法

需求文档 7.1节写的是"四个方法"，但设计时发现`get_access_token`跟另外三个方法性质不同——它是被其他三个方法在内部调用的基础设施，不是直接暴露给业务代码（`sub_tag_node.py`等）使用的接口。所以最终设计是**三个公开方法 + 一个内部方法**，四个方法的对应关系没有丢失，只是`get_access_token`降级为`_get_access_token`（下划线前缀表示内部方法）。

| 需求文档方法名 | 本设计对应 | 公开/内部 |
|---|---|---|
| `get_access_token` | `_get_access_token` | 内部（被其余三个方法调用，不对外暴露） |
| `notify_user` | `notify_user` | 公开 |
| `create_schedule` | `create_schedule` | 公开 |
| `update_customer_tag` | `update_customer_tag` | 公开 |

### 2.1 类结构与初始化

```python
class WxWorkAPI:
    def __init__(self, corp_id: str, corp_secret: str) -> None:
        self._corp_id = corp_id
        self._corp_secret = corp_secret
        self._access_token: str | None = None
        self._token_expires_at: float | None = None  # time.time() 时间戳
```

`corp_id`/`corp_secret`是"这个企微应用是谁"的固定配置，属于实例创建时就确定、之后不再变化的身份凭证，放进`__init__`。`_access_token`和`_token_expires_at`是运行期间会变化的缓存状态，初始值为空，第一次调用时才会被填充。

**为什么用`time.time()`时间戳而不是`datetime`对象**：判断token是否过期只需要做一次数字大小比较（`time.time() < self._token_expires_at`），时间戳是纯数字，比较直接、没有时区处理的复杂度；`datetime`对象要考虑时区（`naive`/`aware`混用是Python常见坑）、格式转换，对这个场景是不必要的开销。

### 2.2 `_get_access_token()`——内部方法，token获取与缓存

```python
def _get_access_token(self) -> str:
    """
    若缓存token未过期（预留5分钟缓冲），直接返回缓存值；
    否则 mock 一次"corp_id + corp_secret 换 token"的企微调用，缓存2小时。
    换取失败时抛 WxWorkAPIError，不返回 None。
    """
```

**缓存判断逻辑**：企微真实access_token有效期是2小时，如果每次调用都重新换取，一是没必要地增加请求次数，二是mock场景下也不真实（真实企微场景频繁换token本身会触发企微侧的频率限制）。所以用单例（见第四节）+ 缓存token字符串+过期时间戳，同一个`WxWorkAPI`实例内所有方法共享同一份缓存。

**为什么提前5分钟就视为过期**：如果卡着"还剩1秒"才判断过期，存在一种竞态可能——判断时还没过期，但实际发起请求时（哪怕mock场景耗时极短，未来换成真实网络请求会有明显耗时）token已经过期了。提前一小段缓冲时间，避免"刚判断完有效，用的时候已失效"这种边界情况。

**失败处理**：换token失败时**抛出自定义异常`WxWorkAPIError`，不返回`None`**。原因见第三节的异常分层设计。

### 2.3 三个公开方法

```python
def notify_user(
    self,
    user_ids: list[str],
    content: str,
    message_type: str = "text",
) -> dict:
    """取得token后，mock向指定企微成员发送文本通知。"""

def create_schedule(
    self,
    organizer_user_id: str,
    attendee_user_ids: list[str],
    start_time: datetime,
    end_time: datetime,
    summary: str,
    description: str = "",
) -> dict:
    """取得token后，mock创建一个包含组织者、参与人、时间和内容的日程。"""

def update_customer_tag(
    self,
    external_user_id: str,
    add_tag_ids: list[str],
    remove_tag_ids: list[str],
) -> dict:
    """取得token后，mock将客户标签的新增和移除变更同步到企微。"""
```

三个方法内部第一步都是调用`self._get_access_token()`拿token，然后构造mock返回数据。**参数设计对齐各自的业务语义**：`notify_user`需要知道通知谁（`user_ids`，支持批量）、说什么（`content`）；`create_schedule`需要组织者、参与人列表、起止时间、主题、可选的详细描述；`update_customer_tag`需要客户是谁（`external_user_id`）、新增哪些标签、移除哪些标签——这三个参数正好和`sub_tag_node.py`里`confirm_tag_batch`函数写Store时用的`confirmed_add_tag_ids`/`confirmed_remove_tag_ids`一一对应，接入时不需要额外转换。

### 2.4 统一返回结构

四个方法（三个公开+一个内部，虽然`_get_access_token`对外返回的是token字符串本身，不是这个结构）中，三个公开方法统一返回：

```python
{
    "success": bool,
    "errcode": int,
    "errmsg": str,
    "data": dict | None,
}
```

`success`是调用方（`sub_tag_node.py`等）唯一需要关心的字段，`errcode`/`errmsg`模仿企微真实API的返回习惯（企微接口普遍用`errcode`/`errmsg`，`errcode=0`表示成功），`data`装每种方法各自的业务结果（mock场景下是构造的假数据，例如`update_customer_tag`成功时`data`里可以放`{"external_user_id": ..., "tags_synced_at": ...}`）。

统一结构的好处：调用方不需要针对三个不同方法写三套不同的解析逻辑，只需要：

```python
result = wechat_tool.update_customer_tag(...)
if not result["success"]:
    # 记录同步失败，或决定后续重试
    ...
```

## 三、异常分层设计：基础设施失败 vs 业务失败

这是本次设计的核心判断点，用一个类比说清楚区别：去银行办业务，"银行今天没开门"（连业务都无法启动）和"银行开着门，但你账户余额不足取不出钱"（业务正常走完，只是结果不如意）是两种性质完全不同的失败，处理方式也应该不同。

### 3.1 两类失败的判断标准

| | 基础设施失败 | 业务失败 |
|---|---|---|
| 例子 | `_get_access_token()`换token失败（corp_secret错误/mock网络超时） | 客户ID在企微不存在、标签ID无效、日程时间冲突 |
| 性质 | 连"跟企微建立起可信身份"这一步都没做成，后续所有操作都没有意义 | 企微服务器正常响应，请求被正常处理，只是业务结果是"办不成" |
| 处理方式 | **抛异常**（`WxWorkAPIError`） | **返回`{"success": False, ...}`**，不抛异常 |
| 原因 | 如果不中断，代码会带着空/无效token继续往下跑，在更隐蔽的地方产生难以排查的错误 | 这是正常业务流程的一部分，调用方可以据此记录失败、决定是否重试，不需要用异常打断整个程序 |

### 3.2 具体分层

```python
class WxWorkAPIError(Exception):
    """企微API调用失败（token获取等基础设施层面问题），与业务失败明确区分。"""
    pass
```

```
_get_access_token()
  └─ 基础设施失败（token换取失败） → 抛 WxWorkAPIError

notify_user() / create_schedule() / update_customer_tag()
  └─ 捕获 WxWorkAPIError（token失败）→ 统一返回 success=False, errcode=40001
  └─ mock 模拟业务失败（如客户不存在）→ 直接返回 success=False, errcode=对应业务错误码
  └─ mock 模拟成功 → 返回 success=True, errcode=0
```

**为什么`_get_access_token()`失败要抛异常而不是返回`None`**：如果返回`None`，三个公开方法必须每次都手动检查"token是不是None"，一旦某处忘记检查，`None`会被当作字符串继续往下传（比如拼进mock的请求参数里），产生的错误现象和真正原因（token没拿到）距离很远，排查成本高。用异常则是**语言层面强制**调用方处理——不捕获就会导致程序在调用处直接崩溃、报错堆栈清晰指向`_get_access_token()`失败这个真正原因，不会被静默传递。

**为什么自定义`WxWorkAPIError`而不是用裸`except Exception`兜底**：如果用`except Exception`捕获所有异常，会把方法名手误打错这类**代码bug**（Python会抛`AttributeError`）也一并伪装成"企微调用失败"返回给调用方，导致调试者去排查企微配置、查网络，却查不到真正原因是代码里有个拼写错误。只精确捕获`WxWorkAPIError`，不属于这个类型的异常（比如`AttributeError`、`TypeError`）会正常往上抛、程序崩溃、控制台给出清晰的报错位置，不会被误伤。

### 3.3 各方法对应的mock异常场景（供第四节测试设计参照）

- `_get_access_token()`：mock`corp_secret`校验失败 → 抛`WxWorkAPIError`
- `notify_user()`：mock成功 / mock`user_ids`中含无效企微成员ID（业务失败）
- `create_schedule()`：mock成功 / mock参与人时间冲突（业务失败）
- `update_customer_tag()`：mock成功 / mock`external_user_id`在企微不存在（业务失败）
- 三个公开方法还需各验证一次：token获取失败时（`_get_access_token`抛异常），公开方法能正确捕获并转换成`success=False`返回，而不是让异常继续往上抛

## 四、单例设计

```python
from functools import lru_cache

@lru_cache
def get_wxwork_api() -> WxWorkAPI:
    """创建并缓存全项目共用的企微API客户端实例。"""
    corp_id = os.getenv("WXWORK_CORP_ID")
    corp_secret = os.getenv("WXWORK_CORP_SECRET")
    if not corp_id or not corp_secret:
        raise RuntimeError("未读取到 WXWORK_CORP_ID/WXWORK_CORP_SECRET，请检查 .env 文件")
    return WxWorkAPI(corp_id=corp_id, corp_secret=corp_secret)
```

**为什么这里用`@lru_cache`包工厂函数、而不是像`WxWorkAPI`内部那样用手写的实例状态**：这是两个不同层面的"单例"。`llm_setting.py`的`get_llm()`同样用`@lru_cache`，模式完全一致——目的是保证全项目所有调用方拿到的是**同一个`WxWorkAPI`实例**，从而共享同一份`_access_token`/`_token_expires_at`缓存，不会出现"每次调用都new一个新实例、缓存形同虚设"的问题。`WxWorkAPI`类内部的`_access_token`字段则是这个唯一实例自己维护的可变状态，两者是"外层保证只有一个实例"和"内层实例自己管理状态"的分工，不冲突。

`WXWORK_CORP_ID`/`WXWORK_CORP_SECRET`两个环境变量目前是mock场景的占位配置（真实值目前不存在，因为没有申请企微测试账号），`.env`里可以先填任意占位字符串，不影响mock方法的运行——mock方法根本不会真的拿这两个值去发网络请求。
