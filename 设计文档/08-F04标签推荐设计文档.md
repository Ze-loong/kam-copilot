## 一、先回答一个问题：为什么不能直接抄F01？

`kam_node.py` 底部留了一行TODO注释："抄上面 `call_profile_subgraph` 的映射写法即可"。这句话对了一半——**主图这一层的接线方式**（意图路由、State传参、包装节点的角色）可以照抄；但**子图内部怎么用`interrupt()`**，F04和F01必须不一样。原因要从F01当初为什么要改说起。

### 1.1 F01现在的架构，是踩坑踩出来的

画像子图刚开始的设计是"一次`invoke()`处理全部字段"：一次 LLM 调用生成多个字段草稿，子图内部用`Send()`并行扇出5个分支，每个分支各自`interrupt()`一次，5条中断一起冒泡给主图。这个设计后来在8月11日被推翻，原因是撞上了LangGraph的真实框架边界：**同一个子图执行实例内，多个字段的interrupt同时pending，此时恢复其中一个、该分支又动态`Send()`出一个新的interrupt（也就是recreate场景），这个新产生的interrupt不会正确出现在当次`invoke()`的返回值里**。这不是代码写错了，是官方"挂载子图"的标准用法在这个组合场景下都会踩，用最小复现脚本验证坐实过。

修复方案是：把"一次子图处理全部字段"改成"每个字段各自开一个独立`thread_id`，各自`invoke()`一次子图，每个子图执行实例从头到尾只处理1个字段"。这样每个子图实例永远只有1个pending interrupt，recreate产生新interrupt时不会有别的interrupt在旁边一起pending，框架边界不会被触发。

### 1.2 F04压根不会踩到这个坑，所以不需要这套架构

关键区别列出来看：

| | F01画像生成 | F04标签推荐 |
|---|---|---|
| 确认动作 | ok / discard / **recreate** | 勾选 / 不勾选（只有这一种，无recreate） |
| 是否有"重新生成产生新interrupt"这个场景 | 有（recreate分支） | **没有** |
| 单次任务里有几条待确认项 | 多个字段，且各自独立确认 | 一批标签，作为整体一次性提交 |
| 用户视角的操作 | 逐字段看、逐字段确认 | 看整批推荐列表，勾选后一次性提交 |

F01需要"每字段独立thread_id"，根本原因是recreate会在同一个执行实例里制造"多pending interrupt+动态Send"这个组合。F04**没有recreate**，也不是"逐条确认"而是"整批看完后一次性提交"，所以从设计源头上就不存在那个组合条件——如果照抄F01的逐字段独立thread_id模式，等于是在没有recreate的场景里，硬套一个专门为了解决recreate副作用而生的架构，纯粹的过度设计。

**结论（已与项目设计确认）：F04用"整批一次`interrupt()`"的方式**——子图一次`invoke()`生成全部推荐标签，作为一个列表整体`interrupt()`一次，前端展示整批、用户勾选后一次性提交，子图`resume`一次、写Store一次。

## 二、需求原文与三个设计判断点

标签推荐的处理流程：

> 1. 用户输入标签推荐意图。
> 2. 系统加载标签体系（从`tags_setting`命名空间读取）和客户行为数据。
> 3. LLM分析客户行为特征与各标签的匹配度，推荐新增标签和待移除标签。
> 4. 系统通过`interrupt()`暂停，向用户展示推荐结果（含推荐理由）。
> 5. 用户确认后，系统更新 Store 中 `external_user.tags`；企微标签同步属于 F15 规划。

需求确认单补充了一条关键约束（备注栏）："标签体系需双方确认"，且01号需求文档已有设计结论：**标签是"贴/不贴"二元判断，不用置信度打分**——这点和画像字段的置信度五元组（value/confidence/source/status）不同，标签只需要"要不要贴"这一个判断维度。

从这段原文和已有结论出发，本轮和项目设计过了三个设计判断点：

### 判断点1：interrupt粒度——整批 vs 逐条

已在第一节讲清楚，结论：**整批一次interrupt**。

### 判断点2：要不要区分"建议新增"和"建议移除"

SRS原文明确写"推荐新增标签和待移除标签"，是两类。要判断"移除"，前提是LLM得先知道客户当前已经有哪些标签——不知道现状，无法建议"移除"什么。

**结论：区分新增和移除。** 这意味着：
- prompt 需要同时喂入客户当前标签和标签体系全集（`tags_setting` 的六组 29 个标签）；
- LLM输出要分成两组：`add`（建议新增）和`remove`（建议移除）；
- 前端展示、State字段、勾选逻辑都要按两组分别处理，但操作方式一致（勾选/不勾选），不是两套不同的交互。

### 判断点3：确认后要不要同步调企业微信API

SRS流程第5步写"用户确认后，系统调用企业微信API更新客户标签"。但F15企业微信集成是排在F04之后的任务（本阶段"F04→F02→F15"顺序里的最后一项），现在还没有`wechat_tool.py`。

**结论**：当前确认动作只更新 Store；企微同步留到 F15 接入阶段。这样标签推荐与外部平台调用各自独立，企微接口失败也不会混入现有确认逻辑。

## 三、State与子图结构设计

### 3.1 目录结构

新建三个文件，对齐`kam_sub_graph_profile/`的组织方式，放进已存在的空目录`kam_sub_graph_tag/`：

```
kam_agent/src/graphs/kam_graph/kam_sub_graph_tag/
├── sub_tag_graph.py    # 图定义（编译成独立graph对象）
├── sub_tag_node.py     # 节点函数
└── sub_tag_state.py    # 子图自己的State（TypedDict）
```

### 3.2 `sub_tag_state.py` —— TagSubState设计

对比画像子图State（`ProfileSubState`）会发现结构简单很多，因为没有recreate、没有per-field循环：

```python
from typing import TypedDict


class TagRecommendation(TypedDict):
    """单条标签推荐的结构：标签ID/名称 + 推荐理由，没有置信度。"""
    tag_id: str
    tag_name: str
    reason: str          # LLM给出的推荐理由，对应SRS"含推荐理由"


class TagSubState(TypedDict):
    # 定位信息：写回 Store 时需要
    follow_user_id: str
    external_id: str

    # 生成推荐时需要的素材：客户当前标签 + 标签体系全集 + 客户行为数据
    current_tags: list[str]        # 从 external_user.tags 读到的当前标签ID列表
    tag_catalog: list[dict]        # tags_setting 命名空间的标签体系全集
    wxqy_msgs: list
    wxkf_msgs: list
    orders: list

    # LLM生成的推荐结果，整批interrupt时作为value的一部分
    add_recommendations: list[TagRecommendation]     # 建议新增
    remove_recommendations: list[TagRecommendation]  # 建议移除

    # 用户勾选后提交的最终结果：只有"哪些标签id最终生效"，不需要逐条状态
    confirmed_add_tag_ids: list[str]
    confirmed_remove_tag_ids: list[str]
```

**没有`confidence`/`status`字段**——这是和`ProfileFieldItem`最直观的区别，呼应"标签是二元判断不用置信度"这条已有结论。也**没有`field_updates`这种逐项状态字典**，因为不是逐项确认，只有"这次提交最终生效了哪些标签"这一个整体结果。

### 3.3 `sub_tag_node.py` —— 节点函数设计

只需要两个节点，比画像子图（`confirm_one_field` + `regenerate_one_field`两个节点、还要处理recreate循环）更简单：

```python
"""
标签推荐子图的节点函数。

与画像子图（kam_sub_graph_profile）的关键区别：
- 没有recreate分支，不需要 Command(goto=Send(...)) 动态路由那一套。
- 一次 invoke() 只产生 1 条 interrupt（整批标签列表打包成一个 value），
  不是"每个字段各自的子图实例各产生1条"。
- 因为没有recreate，也就不会出现"同一执行实例多个interrupt同时pending"，
  天然不会触碰 F01 当初踩的那个 LangGraph 框架边界，不需要"每条推荐各自
  独立 thread_id"这种设计。
"""

from langgraph.types import interrupt

from src.graphs.kam_graph.kam_sub_graph_tag.sub_tag_state import TagSubState
from src.llm.llm_suggest_tag import suggest_tag_recommendations
from src.store.store_client import get_external_user, upsert_external_user


def generate_tag_recommendations(state: TagSubState) -> dict:
    """
    调LLM生成整批标签推荐（新增+移除两组），不涉及交互。

    对应主图 call_tag_subgraph 传进来的 current_tags/tag_catalog/wxqy_msgs/
    wxkf_msgs/orders，一次 LLM 调用产出两组推荐列表。
    """
    result = suggest_tag_recommendations(
        current_tags=state["current_tags"],
        tag_catalog=state["tag_catalog"],
        wxqy_msgs=state["wxqy_msgs"],
        wxkf_msgs=state["wxkf_msgs"],
        orders=state["orders"],
    )
    return {
        "add_recommendations": result["add"],
        "remove_recommendations": result["remove"],
    }


def confirm_tag_batch(state: TagSubState) -> dict:
    """
    整批interrupt一次：把两组推荐列表打包成一个value抛给前端。

    用户在前端勾选完，提交时带回"最终确认的 add/remove 标签id列表"
    （允许用户在推荐基础上取消勾选某些项，不是"全有或全无"）。
    resume 的 value 直接是这个提交结果的 dict，不像F01那样是单个
    "ok/discard/recreate"字符串。
    """
    submission = interrupt(
        {
            "add_recommendations": state["add_recommendations"],
            "remove_recommendations": state["remove_recommendations"],
        }
    )

    confirmed_add_tag_ids = submission.get("confirmed_add_tag_ids", [])
    confirmed_remove_tag_ids = submission.get("confirmed_remove_tag_ids", [])

    # 写回 Store：在当前 tags 基础上加上确认新增的、去掉确认移除的
    external_user = get_external_user(state["follow_user_id"], state["external_id"])
    current_tags = set(external_user.value["tags"]) if external_user else set()
    new_tags = (current_tags | set(confirmed_add_tag_ids)) - set(confirmed_remove_tag_ids)

    upsert_external_user(
        external_id=state["external_id"],
        union_id=external_user.value["union_id"],
        follow_user_id=state["follow_user_id"],
        name=external_user.value["name"],
        remark_name=external_user.value["remark_name"],
        tags=list(new_tags),
    )

    # TODO（F15完成后在这里插入）：
    # wechat_tool.notify_tag_update(external_id, confirmed_add_tag_ids, confirmed_remove_tag_ids)
    # 现阶段只写Store，企微同步留空，理由见 08号设计文档 判断点3

    return {
        "confirmed_add_tag_ids": confirmed_add_tag_ids,
        "confirmed_remove_tag_ids": confirmed_remove_tag_ids,
    }
```

`suggest_tag_recommendations` 的生成、校验和单选组兜底见第五节。

### 3.4 `sub_tag_graph.py` —— 图定义

```python
from langgraph.graph import START, StateGraph

from src.graphs.kam_graph.kam_sub_graph_tag.sub_tag_node import (
    confirm_tag_batch,
    generate_tag_recommendations,
)
from src.graphs.kam_graph.kam_sub_graph_tag.sub_tag_state import TagSubState

_builder = StateGraph(TagSubState)

_builder.add_node("generate_tag_recommendations", generate_tag_recommendations)
_builder.add_node("confirm_tag_batch", confirm_tag_batch)

_builder.add_edge(START, "generate_tag_recommendations")
_builder.add_edge("generate_tag_recommendations", "confirm_tag_batch")

# confirm_tag_batch interrupt 一次、resume 后直接写 Store 并 return，
# 没有 recreate 分支，不需要 Command(goto=Send(...)) 动态路由，
# 也就不需要在这里注册额外的静态边去接 regenerate 节点。


def build_tag_graph(checkpointer, store):
    return _builder.compile(checkpointer=checkpointer, store=store)
```

注意这里**没有把`generate_tag_recommendations`挪到主图层**（不像F01的`generate_all_field_drafts`被搬到了`kam_node.py`）。F01当初挪上去，是因为要在主图层"生成一次草稿→循环发起N次子图invoke"；F04子图本身从头到尾只invoke一次，生成和确认都在同一次执行里，没有必要拆到主图层，放在子图内部结构更简单、更贴近这个子图"只做一件事"的边界。

## 四、主图接线：为什么"抄映射写法"这句话大致对，但要注意什么

`kam_node.py`需要新增一个包装节点`call_tag_subgraph`，整体映射结构可以参考`call_profile_subgraph`，但内部逻辑简单得多——**不需要循环、不需要拼子thread_id**：

```python
def call_tag_subgraph(state: dict) -> dict:
    """
    包装节点：整批invoke一次标签子图，收集这一条interrupt返回给SSE端点。

    与 call_profile_subgraph 的关键区别：不循环、不需要为每条推荐各自
    开子thread_id——F04子图本来就只invoke一次、只产生一条interrupt，
    直接用主thread_id即可（不需要拼接 f"{main_thread_id}:{field_name}"
    这种子thread_id，因为这里没有"字段"这个概念，是整批）。
    """
    if _tag_graph is None:
        raise RuntimeError("tag_graph 尚未注入——webapp.py 启动时需先调用 set_tag_graph()")

    main_thread_id = state["_main_thread_id"]
    external_user = state.get("external_user")
    current_tags = external_user.value["tags"] if external_user else []
    # 注意：tag_catalog 直接把 search_tags_setting() 的原始 Item 列表传给子图，
    # 不能写成 [item.value for item in tag_catalog] 这种画像子图惯用的取法——
    # tags_setting 命名空间存的时候 tag_id 只作为 Item.key，没有放进 value 里
    # （见 store_client.py upsert_tags_setting，value 只有 tag_name/deleted/
    # strategy_id/group_id/group_name 五个字段），只取 .value 会把 tag_id 丢光。
    # llm_suggest_tag.py 的 _normalize_tag_catalog() 已经做了兼容处理（同时
    # 认 Item.key/.value 和纯 dict 两种形态），这里直接把 Item 列表原样传进去
    # 即可，不要在这一层先自作主张拍平成 [item.value ...]。
    tag_catalog = search_tags_setting()  # tags_setting 命名空间，标签体系全集

    sub_input: TagSubState = {
        "follow_user_id": state["follow_user_id"],
        "external_id": state["external_id"],
        "current_tags": current_tags,
        "tag_catalog": tag_catalog,
        "wxqy_msgs": state.get("wxqy_msgs", []),
        "wxkf_msgs": state.get("wxkf_msgs", []),
        "orders": state.get("orders", []),
        "add_recommendations": [],
        "remove_recommendations": [],
        "confirmed_add_tag_ids": [],
        "confirmed_remove_tag_ids": [],
    }

    # 直接用主 thread_id，不用像F01那样拼子thread_id——
    # 这个子图整个任务只有1次invoke、1条interrupt，没有"多个并行执行实例"
    # 需要靠不同thread_id互相区分。
    sub_result = _tag_graph.invoke(
        sub_input,
        config={"configurable": {"thread_id": main_thread_id}},
    )

    sub_interrupts = list(sub_result.get("__interrupt__", ()))
    tag_interrupt = None
    if sub_interrupts:
        interrupt_item = sub_interrupts[0]
        tag_interrupt = dict(interrupt_item.value)
        tag_interrupt["interrupt_id"] = interrupt_item.id
        tag_interrupt["thread_id"] = main_thread_id

    return {"tag_interrupt": tag_interrupt}
```

这一点是"抄映射写法"这句TODO提示需要修正的地方：F01的映射写法核心是"循环+子thread_id"，这套是专门为了解决多字段各自recreate而存在的，F04不需要循环、也不需要子thread_id，只是"包一层，转发子图的invoke结果"这个最外层结构相似而已。如果照字面意思整段复制，会把不必要的循环和子thread_id拼接逻辑也搬过来，属于该做减法却做了加法。

主图`MainState`（`kam_graph.py`）需要新增一个字段`tag_interrupt: dict | None`，`route_by_intent`需要能路由到`tag_subgraph`分支（目前只有`profile`一条分支，`detect_intent`固定返回`{"intent": "profile"}`，接入F04时要让它能识别"标签推荐"意图，这部分和F02一起做意图识别升级更合适，本次先把tag分支的路由目标注册上、`detect_intent`暂时保持MVP的固定返回也可以，取决于要不要现在就让意图识别可用——这个留给实现时再判断，不影响子图本身的设计）。

## 五、`llm_suggest_tag.py` 与单选组兜底

LLM 根据客户证据与标签目录提出新增、移除建议。返回值先做标签白名单与结构校验，再由 `_enforce_single_select()` 确保每个单选组最多新增一个标签；若同组存在旧标签且模型未建议移除，代码补充移除建议。多选组保留多个有证据的推荐。模型建议通常不超过三项，顾问仍须整批确认。

## 六、kam_admin对接：`/api/tags/suggestions/<external_id>`

现状（`kam_admin_app.py` 314-317行）：

```python
@app.route("/api/tags/suggestions/<external_id>", methods=["GET"])
@login_required
def api_tag_suggestions(external_id):
```

这条路由是GET，但F04的真实交互流程需要"发起推荐任务→轮询/SSE拿结果→提交勾选"，单一个GET接口不够用，和F01当初"只发thread_id，SSE另起连接"的思路类似，需要参考`/tasks/generate_profile`+`/tasks/stream`+`/tasks/confirm`的三段式模式设计对应的标签接口，而不是简单把这个占位GET改成一个同步阻塞调用（同步调用会在LLM推理期间把请求卡住，且拿不到`interrupt_id`供后续提交用）。具体接口形状（是复用`/tasks/*`三个接口加一个`task_type`参数区分，还是新开`/tasks/tag/*`一组接口）留到实现阶段和kam_admin调用方一起定，本文档先标注这里不是简单改一行返回值就能完事的。

## 七、验收标准
