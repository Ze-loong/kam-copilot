## 一、和F04的关系：能抄什么、不能抄什么

`kam_node.py` 底部TODO注释提示"F02同样没有recreate，结构会比F04更简单，参考 `call_tag_subgraph` 的整批invoke思路"。08号F04设计文档结尾也留了一句话："F02开始时，`detect_intent` 需要同时支持 profile/tag/chat_suggestion 三个分支，届时一并升级为真正的意图判断。"这两条线索本次开工前先核实过，结论：

- **能抄**：主图接线的"包装节点整批invoke一次子图"这个外层结构，和F04的`call_tag_subgraph`一致。
- **能抄**：不需要recreate分支，不需要`Command(goto=Send(...))`动态路由。
- **不能直接抄**：F02**没有interrupt**（区别于F04的"没有recreate但仍有interrupt"），子图从`invoke()`到`return`是一次性跑完，这是本文档要重点讲清楚的架构差异点。
- **不能直接抄**：F04是"一个子图内部用`add`/`remove`两组处理"，F02/F03是"两个完全独立的子图"，判断依据在第二节详细展开。

## 二、需求原文与四个设计判断点

回复建议的处理流程：

> 1. 用户输入意图（如"回复建议"或点击菜单按钮）。
> 2. 系统加载对应的聊天记录作为上下文，同时加载客户画像和基本信息以辅助分析。
> 3. LLM分析对话上下文、客户意图和情绪状态，生成回复建议（`SuggestionChat`/`SuggestionKF`）及推理说明。
> 4. 建议内容通过状态字段传递至主图的`task_result`，经由SSE流式传输至侧边栏，实时展示给用户。

后置条件："建议仅展示，不自动保存或发送至企业微信，最终发送行为由用户手动操作完成。"——这是F02/F03与F01/F04最根本的架构分野：**没有需要冻结等待的人工确认环节**。

### 判断点1：F02.1（销售）和F02.2（客服）要不要共用一个子图？

已与项目设计过了这个判断点，结论：**两个完全独立的子图**（各自的`state`/`node`/`graph`三件套），对齐SRS原文写的`sub_chat_suggestion_graph`（销售）/`sub_kf_chat_suggestion_graph`（客服）两个子图名。

判断依据，与F04的"一个子图内部用两组结果处理"对比：

| | F04新增/移除 | F02销售/F03客服 |
|---|---|---|
| 数据来源 | 同一份数据（`current_tags`+`tag_catalog`+行为数据） | 完全不同（`wxqy_msgs`销售聊天 vs `wxkf_msgs`客服聊天，两个独立命名空间） |
| LLM调用次数 | 1次调用，1次分析同时产出两个维度结果 | 各自独立调用，两次分析面对完全不同的输入和目标 |
| 本质 | 一个判断过程的两个输出维度 | 两个平行的业务能力 |
| 是否可能独立演化 | 不会（新增/移除天然成对） | 会（SRS原文："客服聊天记录来源于企业微信「微信客服」功能，与销售聊天记录来源不同……系统通过独立的子图专门处理"，未来客服场景大概率接工单系统、销售场景大概率接CRM，各自独立扩展） |

如果用一个子图+`scene`字段区分销售/客服，state里会出现"销售用得到的字段（客户画像、订单）客服不用画像，客服记录销售又用不到"这种半数字段常年为空的畸形结构，是该做减法（拆分）却做了加法（合并）的反例。

### 判断点2：需不需要interrupt？子图需不需要独立`thread_id`？

**结论：都不需要。**

先明确因果链：`interrupt()`的本质是"冻结子图执行到某个中间点，等待未来某次带着正确`thread_id`的请求把它恢复"；checkpointer存在的意义就是"记住这个执行实例停在哪、状态是什么"。F04当初需要给标签子图单独拼`thread_id`（`f"{main_thread_id}:tag"`），根因是它会`interrupt()`——如果直接用`main_thread_id`，主图跑到`END`时写自己的checkpoint会把标签子图interrupt时留下的checkpoint覆盖掉，等`/tasks/confirm_tags`再来resume时读到的就是被覆盖过的空数据（真实联调复现过的坑）。

F02/F03**没有interrupt**——子图从加载聊天记录到LLM生成建议到`return`是一次性跑完的，不存在"将来要靠某个`thread_id`把它找回来恢复执行"这件事。没有暂停就没有"读旧checkpoint"这个动作，自然也没有"旧checkpoint被覆盖"的风险。讨论"要不要防止checkpoint覆盖"这个问题在F02场景下本身就不成立。

落地结论：`call_chat_suggestion_subgraph`/`call_kf_chat_suggestion_subgraph`直接用`main_thread_id`（或者严格说，`compile()`甚至不强制要求传`checkpointer`——但为了和项目里所有子图保持接口一致、以及给`store`参数使用，仍然统一传`checkpointer`+`store`，只是不依赖它的"冻结恢复"能力）。

### 判断点3：怎么区分"这次请求是销售场景还是客服场景"？

SRS原文："用户输入意图（如'回复建议'或点击菜单按钮）"——字面看像是要靠意图识别/LLM分类。但已与项目设计确认沿用F04确立的原则：**意图判断交给路由层（不同接口/不同URL），不靠LLM猜**。

具体做法与F04当初的`detect_intent`设计完全一致（`kam_node.py`第53-58行原话："接口层已经用不同的URL区分'这是画像请求还是标签请求'，不需要靠这个节点去猜或调LLM分类"）：

- `kam_sidebar`销售场景菜单调 `/tasks/generate_chat_suggestion`，客服场景菜单调 `/tasks/generate_kf_chat_suggestion`，两个接口各自在发起主图`invoke()`时把`intent`显式写死传入初始State（`"chat_suggestion"`/`"kf_chat_suggestion"`）。
- `detect_intent`继续保持"透传state里已有的intent，没有则兜底profile"的现有逻辑不变，不需要新增分类判断代码。
- `route_by_intent`新增两条分支：`chat_suggestion`→`chat_suggestion_subgraph`，`kf_chat_suggestion`→`kf_chat_suggestion_subgraph`。

不采用"靠员工角色自动判断走哪个子图"的方案，因为角色和场景不是严格一一对应的（同一个顾问理论上也可能需要客服口径的建议），接口区分更明确、不引入猜测风险，也和F04已确立的模式保持一致，不增加系统整体设计复杂度。

### 判断点4：结果怎么传给前端？

SRS原文明确："建议内容通过状态字段传递至主图的`task_result`，经由SSE流式传输至侧边栏"——不像F01/F04要走`__interrupt__`+`interrupt_id`+`/tasks/confirm`的确认闭环，F02/F03的子图`invoke()`跑完直接拿到最终结果，主图把结果放进`task_result`字段，SSE端点直接推送，前端展示即结束，没有后续的确认/提交步骤。

### 3.2 `sub_chat_suggestion_state.py`（销售场景）

```python
from typing import TypedDict


class ChatSuggestionState(TypedDict):
    # 定位信息
    follow_user_id: str
    external_id: str

    # 生成建议需要的素材：SRS 3.2.1 所需数据输入——
    # 员工信息、聊天历史、订单历史、客户信息、客户标签、客户画像
    external_user: dict | None   # 含 tags
    profile: dict | None
    wxqy_msgs: list              # 销售聊天记录（企业微信）
    orders: list
    solution_refs: list          # 产品与解决方案资料检索片段

    # LLM生成结果：建议文本 + 推理说明
    suggestion_text: str
    reasoning: str
```

没有`add_recommendations`/`confirmed_xxx_ids`这类推荐-确认对，也没有`interrupt`相关字段——因为不需要交互闭环，`generate`节点跑完直接是终态。

### 3.3 `sub_kf_chat_suggestion_state.py`（客服场景）

```python
from typing import TypedDict


class KfChatSuggestionState(TypedDict):
    follow_user_id: str
    external_id: str

    # 老客客服应答读取客户信息、客服聊天与订单；不使用画像和标签推断。
    external_user: dict | None
    wxkf_msgs: list             # 客服聊天记录
    orders: list                # 已购设备及交付、维保历史

    suggestion_text: str
    reasoning: str
```

**两个 State 的输入不同**：销售读取画像、企微聊天、订单及产品方案资料检索片段；客服读取客服聊天和订单，不读取画像。订单能为老客的交付、维保、扩容问题提供事实依据，画像不应用来替代服务事实。这印证了判断点1"两者是平行业务能力而非同一份数据的两种分类"——如果字段集合本该相同，那就该合并成一个子图。

### 3.4 `sub_chat_suggestion_node.py`（销售场景，客服场景结构对称）

```python
"""
销售聊天回复建议子图的节点函数。

与F04(标签)/F01(画像)的关键区别：没有interrupt和确认闭环。
检索节点先查产品方案资料，generate 节点随后产出终态。
"""

from src.graphs.kam_graph.kam_sub_graph_chat_suggestion.sub_chat_suggestion_state import (
    ChatSuggestionState,
)
from src.llm.llm_suggest_chat import suggest_chat_reply


def generate_chat_suggestion(state: ChatSuggestionState) -> dict:
    """
    调LLM生成回复建议+推理说明，一次性产出终态，不涉及交互。
    """
    result = suggest_chat_reply(
        external_user=state.get("external_user"),
        profile=state.get("profile"),
        wxqy_msgs=state.get("wxqy_msgs", []),
        orders=state.get("orders", []),
        solution_refs=state.get("solution_refs", []),
    )
    return {
        "suggestion_text": result["suggestion_text"],
        "reasoning": result["reasoning"],
    }
```

`llm_suggest_chat.py` 已实现制造业新客/老客回复规则，见第五节。

## 四、主图接线

`kam_node.py`需要新增两个包装节点，结构对齐`call_tag_subgraph`（整批invoke一次），但比它更简单——不需要处理`__interrupt__`：

```python
def call_chat_suggestion_subgraph(state: dict) -> dict:
    """
    包装节点：invoke一次销售回复建议子图，结果直接放进 task_result。

    与 call_tag_subgraph 的关键区别：没有 interrupt，不需要检查
    sub_result.get("__interrupt__")、不需要收集 interrupt_id/thread_id
    ——invoke() 返回的就是最终结果，直接取出来即可。
    """
    if _chat_suggestion_graph is None:
        raise RuntimeError(
            "chat_suggestion_graph 尚未注入——webapp.py 启动时需先调用 "
            "set_chat_suggestion_graph()"
        )

    main_thread_id = state["_main_thread_id"]

    sub_input: ChatSuggestionState = {
        "follow_user_id": state["follow_user_id"],
        "external_id": state["external_id"],
        "external_user": state.get("external_user"),
        "profile": state.get("profile"),
        "wxqy_msgs": state.get("wxqy_msgs", []),
        "orders": state.get("orders", []),
        "suggestion_text": "",
        "reasoning": "",
    }

    # 没有interrupt，不需要拼子thread_id，直接用主thread_id即可
    # （判断点2：没有暂停就没有"读旧checkpoint被覆盖"的风险）。
    sub_result = _chat_suggestion_graph.invoke(
        sub_input,
        config={"configurable": {"thread_id": main_thread_id}},
    )

    return {
        "task_result": {
            "type": "chat_suggestion",
            "suggestion_text": sub_result["suggestion_text"],
            "reasoning": sub_result["reasoning"],
        }
    }

```

`MainState`（`kam_graph.py`）需要新增字段：

def route_by_intent(state: dict) -> str:
    if state["intent"] == "profile":
        return "profile_subgraph"
    if state["intent"] == "tag":
        return "tag_subgraph"
    if state["intent"] == "chat_suggestion":
        return "chat_suggestion_subgraph"

## 五、`llm_suggest_chat.py` 的输入与约束

F02 读取客户画像、企微聊天、订单，并用客户最近三条企微消息检索 `solution` 类产品方案资料。检索分数低于 F16 共用阈值的片段不进入 Prompt；没有客户消息或向量库异常时传空列表，继续生成建议。F02 判断技改项目阶段、对话对象在决策链中的角色及顾虑；引用通用交付周期等资料时须保留“参考、以合同为准”等限定，不得凭空承诺价格、交期或设备效果。F03 读取客服聊天和订单中的已购设备、交付与维保历史，不读取画像，避免把销售推断当作服务事实；故障问题先索取定位信息，非扩容问题不主动推销。两个函数均返回建议文本与推理说明，顾问自行发送。

## 七、验收标准
